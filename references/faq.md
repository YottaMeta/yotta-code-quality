# 元质常见问题

## 速查索引

- **触发**：什么时候用 · 每次都读全部文档吗
- **评审**：评分怎么算 · 大 PR 怎么办 · 没有测试怎么办
- **集成**：CI / hook 怎么接
- **边界**：和编译器 / 测试的关系 · 输出格式

---

## 1. 什么时候应该触发？

用户要求 review、检查代码质量、判断是否可合并、识别技术债、评估测试质量，或在发布前做质量门时触发。

## 2. 每次都要读全部参考文档吗？

不需要。先读 `SKILL.md`，按模式加载：日常 review 读 `pr-review-guide.md` 与 `common.md`；需要风险定义时读 `decay-risks.md` / `test-decay-risks.md`；发布或 UX 专项再读 `editorial-extensions.md`。

## 3. 健康分怎么算？

按发现数量与严重度加权，具体公式和报告模板在 `references/common.md`。分数用于趋势比较，不替代人工判断。

## 4. 发现必须按什么格式写？

使用 Iron Law 四段：Symptom → Source → Consequence → Remedy。缺少任一段应补齐后再输出。

## 5. 大 PR 怎么处理？

先分层：入口 / 配置 / 数据流 / 测试 / 文档。优先 R2（正确性），再看 R1 / R3 / R4；只对高风险路径展开全文，不在低风险格式化改动上消耗篇幅。

## 6. 没有测试的项目怎么评审？

明确标注“测试信号缺失”，并把它作为发现输出；不要假设测试通过。可建议最小回归清单。

## 7. 可以接入 CI 或 hook 吗？

可以。`references/hooks.json` 提供危险命令拦截示例，`references/AGENTS-template.md` 可作为仓库规则模板。接入前先在本地试运行。

## 8. 发现太多时怎么排序？

按 Blocker > Major > Warning > Suggestion。同级里先输出影响正确性和发布安全的发现。

## 9. 它会替代编译器或测试吗？

不会。元质负责评审决策与风险解释；编译、测试、运行验证仍由对应工具完成。

## 10. 输出可以直接贴到 PR 吗？

可以。按 `references/common.md` 的模板输出，包含健康分、发现清单与复核建议。
